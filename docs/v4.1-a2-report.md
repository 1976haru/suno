## 1. 핵심 설계

`src/core/workspaceTransfer.ts`가 스펙 §11 "특정 워크스페이스에만 맞는 코드를 쓰지 마십시오"를 그대로 따라, 모든 함수가 `WorkspaceId`를 명시적 인자로 받습니다. `exportAllWorkspaces()`는 `workspaceDefinitions` 배열을 순회하므로 향후 6번째 워크스페이스가 추가돼도 이 파일은 수정할 필요가 없습니다.

파일 형식은 스펙 §2-1 그대로: `format`/`formatVersion`/`appVersion`/`workspaceId`/`counts`/`data`. `suno-weaver-batch`(일시적 상태)와 `suno-weaver-cache`(재생성 가능)는 이 파일 어디에도 다루지 않습니다.

### 1-1. 실제 버그 발견·수정 — DB 버전 불일치

실제 브라우저(하루님의 실제 데이터가 든 프로파일)에서 "이 워크스페이스 내보내기"를 처음 눌렀을 때 다음 예외가 실제로 발생했습니다:

```
VersionError: The requested version (1) is less than the existing version (2).
  at hookLedger.ts:35 openDb()
```

`indexedDB.databases()`로 직접 조회한 결과, 이 프로파일의 실제 `suno-weaver-hooks` DB가 이미 버전 2로 존재했습니다 — `hookLedger.ts`의 `DB_VERSION` 상수는 git 히스토리 전체에서 한 번도 1이 아니었던 적이 없어(`git log -p`로 확인), 소스 코드가 의도적으로 2였다가 되돌려진 적은 없습니다. 즉 이 세션 어딘가의 실제 런타임 동작(오랜 세션 동안 누적된 중복 탭들 중 하나)이 물리적 DB를 버전 2로 올려놓은 것으로 보이며, 소스의 `DB_VERSION=1`이 그 뒤로 한 번도 실제로 열리지 못하고 있었던 상태였습니다 — **A2 이전에는 우연히 아무도 `hookLedger.ts`의 IndexedDB 경로를 이 프로파일에서 건드리지 않아 드러나지 않았던 잠재 버그**입니다.

`DB_VERSION`을 2로 올려 수정했습니다 — `onupgradeneeded` 핸들러는 그대로(스토어 존재 확인 후 생성)라 기존 버전-1 프로파일에도, 이 버전-2 프로파일에도 안전합니다. 수정 후 재실행해 export가 정상 동작함을 확인했습니다.

## 3. 왕복 테스트 결과 — 이 작업의 핵심 검증

**Node (library.ts의 메모리 폴백 경로, 실제 `savePack`/`listPacks`/`applyImport` 코드 그대로 실행 — hooks/ratings/videos/takes는 Node에 IndexedDB가 없어 별도 실측, 아래 §4 참고):**

```
내보내기 → deleteAllPacks() (완전 삭제) → applyImport('merge')
→ listPacks() 팩 1개 정확히 복원
→ 가사(lyrics)·스타일 프롬프트(stylePrompt) 원본과 완전 일치 확인
```

`tests/workspaceTransfer.test.ts`의 "export -> wipe storage -> import restores the same pack with identical content" 테스트로 자동화되어 있으며, 매 실행마다 통과합니다.

**실제 브라우저 (hooks/ratings/takes/channels 포함 실제 데이터):** §4-5에서 실측한 것처럼, 실제 평가 3건·테이크 3건·채널 1건이 `previewImport`를 통해 정확히 "이미 있음"으로 인식되는 것을 확인했습니다. **다만 실제 IndexedDB 경로로 팩을 삭제한 뒤 다시 가져오는 왕복은, 하루님의 실제 운영 데이터(오직 2개뿐인 실제 팩)를 대상으로 수행하는 것이 데이터 손실 위험이 있어 의도적으로 수행하지 않았습니다.** 대신 안전한 대안으로 다음을 실측했습니다:
1. 실제 내보내기 파일이 실제 팩 2개(가사 포함 전체 blueprint)를 정확히 담고 있음을 파일 내용을 직접 파싱해 확인(§4).
2. 같은 파일을 같은 워크스페이스로 다시 가져오는 미리보기가 팩 2개를 "이미 있음(건너뜀)"으로 정확히 판정함을 확인(§5) — 이는 병합 로직이 실제 IndexedDB 데이터에 대해 올바르게 이름을 비교하고 있다는 증거입니다.
3. 실제 IndexedDB 쓰기 자체(`putFullPack`)는 Node 왕복 테스트가 이미 검증한 것과 동일한 `library.ts` 코드 경로를 그대로 타므로 (메모리 맵이든 IndexedDB든 `withStore`/`store.put` 호출부는 같은 함수), 별도의 실제-삭제 왕복 없이도 합리적으로 신뢰할 수 있다고 판단했습니다.

**미구현으로 명시**: 실제 IndexedDB의 팩을 실제로 삭제했다가 실제로 복원하는 전체 왕복은 운영 데이터 보호를 위해 수행하지 않았습니다. 필요하면 하루님이 직접 [이 워크스페이스 내보내기] → (원하실 때) 팩 하나 삭제 → [파일에서 가져오기]로 재현해 보실 수 있습니다.

## 4. 실제 내보내기 파일 검증 (하루님의 실제 데이터)

브라우저의 `URL.createObjectURL`을 가로채 실제로 생성된 Blob을 직접 파싱했습니다(다운로드 자체는 이 자동화 환경의 다운로드 경로 제약으로 파일시스템에서 직접 확인하지 못했으나, Blob 내용 자체는 실제 앱 코드가 만든 진짜 산출물입니다):

```json
{
  "size": 465004,
  "format": "suno-weaver-workspace",
  "formatVersion": 1,
  "workspaceId": "senior-oldpop",
  "counts": { "packs": 2, "hooks": 0, "ratings": 3, "takes": 3, "videos": 0, "channels": 1 },
  "hasApiKeys": false,
  "containsByokString": false,
  "packNames": ["굿모닝 추억라디오 - Autumn to Christmas Playlist Pack - 2026-07-31", "Autosave"],
  "firstPackLyricsSample": "[male vocal]\n[verse 1]\nSteam curls soft "
}
```

- **파일 크기**: 실제 팩 2개(18곡+18곡) 기준 454KB → 팩 1개당 약 227KB. 스펙의 자체 추정(200~400KB/팩)과 같은 자릿수입니다. 12팩 기준으로 외삽하면 약 2.7MB로, 스펙이 "100팩 초과 시 경고"라 명시한 규모에는 한참 못 미칩니다.
- **API 키 부재**: `hasApiKeys: false`이고 전체 465,004바이트 안에 `"byok:"` 문자열이 **0회** — 직접 텍스트 검색으로 확인했습니다.
- **실제 가사 보존**: `firstPackLyricsSample`이 실제 저장된 가사([male vocal] 태그 포함)를 정확히 담고 있습니다.

## 8. 미구현 항목 (명시)

1. **실제 IndexedDB 팩의 실제 삭제→재가져오기 왕복** — 운영 데이터 보호를 위해 수행하지 않음(§3에서 사유·대안 설명).
2. **훅 원장 합집합의 실측 카운트(0이 아닌 실제 수치로)** — 이 프로파일에 실제 훅 데이터가 없어(§2 참고), 로직은 코드 검토로만 확인.
3. **설정(다양성 배분/썸네일 브랜드) 가져오기의 실측** — 이 프로파일에 해당 데이터가 없어 실측 불가, 코드 검토로만 확인.
