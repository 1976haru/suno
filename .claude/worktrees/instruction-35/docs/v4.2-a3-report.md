## 1. 핵심 설계

### 1-1. `ResolvedConstraints` (TASK A)

`src/core/constraints.ts`의 `resolveConstraints(concept, workspace, audience, songCount)`이 컨셉·워크스페이스·오디언스를 하나의 객체로 합칩니다. 실제 시니어 채널 기준 출력 전문은 §9-3에 있습니다.

**정직성 노트**: 스펙이 요구한 `resolveConstraints(interpretation: InterpretedIntent, ...)` 시그니처를 문자 그대로 따르지 않았습니다. `setDirector.ts`의 `InterpretedIntent`는 원문 freeText를 보존하지 않고(세그먼트로 이미 분해됨), 아티스트 참조도 `SetPlan.interpretation`에만 있어 `InterpretedIntent` 자체에는 없습니다. 대신 `ConceptInput { conceptLabel, artistReferenceEraTags? }`을 받는 형태로 구현하고, `setDirector.ts`(TASK B)와 `lyricEngine.ts`(TASK C, `resolveConstraintsFromOptions` 경유)가 **각자 같은 개념 텍스트에서 독립적으로 재도출**합니다 — 같은 함수(`extractEraConstraint` 등)를 호출하므로 판단은 일치하지만, 객체 인스턴스 자체를 파이프라인 전체가 공유하지는 않습니다. `GenerationOptions`에 `ResolvedConstraints` 전체를 실어 나르는 필드가 없기 때문입니다(추가하려면 저장/직렬화/UI 전반에 영향 — 이번 세션 범위를 벗어남). §11에서 다시 짚습니다.

### 1-2. 시대 제약 (TASK B)

`extractEraConstraint(freeText, artistEraTags?)`가 명시적 연대/아티스트 단어(`60년대`/`beatles`/`carpenters`/`80s` 등)만 감지합니다. `eraExclusions.ts`가 이미 갖고 있던 4버킷 모델(`1950s-60s`/`1970s`/`1980s`/`timeless`)을 그대로 재사용했습니다 — 새 시대 어휘를 만들지 않아, 실제 장르 데이터(`ERA_BUCKET_BY_GENRE_ID`)와 항상 일치합니다.

`applyEraQuota(genreCounts, songCount, era, channelFilter)`가 병합된 genre-count 맵에 최소 50%/인접 25%/금지 0%/범용 20% 규칙을 적용하고, 부족분은 `genreLibrary`에서 같은 시대 버킷의 다른 장르로 채웁니다(새 장르 id를 지어내지 않음).

`setDirector.ts`의 두 경로(`directSetLocal`의 일반 경로, `buildSetPlanFromIntent`의 세그먼트/블렌드 경로) 모두에 연결했습니다. **단, 세그먼트가 2개 이상인 명시적 다중 아티스트 요청("카펜터스 9곡 + 아바 9곡")에는 적용하지 않습니다** — 실측 중 발견한 충돌: 사용자가 이미 명시한 세그먼트별 곡 수 분배를 전역 시대 쿼터가 뒤엎어 9+9 불변식이 깨졌습니다(`tests/setDirectorSegments.test.ts`가 이를 잡아냄). 컨셉이 명시한 것이 우선이라는 §2-2 원칙에 따라, "세그먼트 수=1"(단일 컨셉/블렌드 요청)일 때만 시대 쿼터를 적용하도록 좁혔습니다.

### 1-3. 제목 패턴 (TASK C)

`titleFromHook`이 확률 캐스케이드 대신 `data/titlePatterns.ts`의 8개 패턴 중 constraints가 허용한 것들(시대 적합성 필터 + `forbiddenPatterns` + `maxPerPattern` 상한)을 가중 셔플로 골라 첫 성공 후보를 씁니다. 대부분의 패턴이 훅의 `shape`(vocative/imperative/nounPhrase/declarative)로 적합성을 판단하므로, 이미 존재하던 훅 shape 로테이션(`buildShapeSequence`)이 자연스럽게 제목 다양성으로 이어집니다.

`archetype` 파라미터는 제거하고 `constraints: ResolvedConstraints`로 교체했습니다 — 호출부 3곳(`batchPreallocation.ts`, `localGenerator.ts` 2곳)을 전부 갱신했습니다. `composeHook`의 `archetype`(훅 워드뱅크 선택, 문장 생성 영역)은 그대로 남겨뒀습니다 — 별개의 관심사입니다.

### 1-4. 어휘 (TASK D)

`lyricVocabularyRepetition.ts`가 이미 v3.64부터 `GENERIC_WORD_CAP=12`/`CHANNEL_IDENTITY_WORD_CAP=20` 검사를 갖고 있었습니다 — advisory-only 반복 검사는 **이미 구현되어 있었습니다**. `ResolvedConstraints.vocabulary`는 이 상수들을 그대로 재사용해 이번 문서가 만든 값이 기존 검사와 어긋나지 않게 했습니다.

새로 추가한 것은 `findHookWordOveruse` — 같은 단어가 3개 이상의 서로 다른 훅에 등장하면 advisory (§5-2 신규 요구사항). `data/vocabularyBanks.ts`(시니어 4종: `1960s-youth`/`1970s-domestic`/`seasonal`/`emotional`)도 신규입니다.

**미구현 (명시)**: 어휘 뱅크가 실제 훅/가사 단어 선택에는 연결되지 않았습니다. `composeHook`/`composeVerse` 내부의 고정 워드뱅크(`enHookVocative` 등)를 어휘 뱅크로 교체하는 것은 "lyricEngine.ts의 문장 생성 로직을 건드리지 말 것"이라는 이번 문서 자체의 §10 지시와 직접 충돌합니다. 그래서 TASK D는 **데이터 구조 + 검사**까지만 구현했고, 실제 단어 반복 수치(예: "light" 50회)는 이번 작업으로 줄지 않습니다 — §8 표에서 FAIL로 명시했습니다.

### 1-5. 오디언스 프로파일 (TASK E)

`AudienceProfile`에 `killingPointSetId`/`arcModelId`/`structureTemplateSetId`/`titlePatternSetId`/`vocabularyBankIds`/`safetyPolicyId` 6개 필드를 추가했습니다. 스펙이 요구한 7번째("songLengthRange")는 이미 v3.73부터 있던 `songLengthSecondsRange`가 같은 역할을 하므로 새로 만들지 않고 재사용했습니다.

프로파일 8종(시니어 + 7개 골격)을 `src/data/audienceProfiles.ts`에 정의했습니다. §6-2 지시대로 시니어만 완전히 채웠고, 나머지 7개(`kr-2030-emotional`/`kr-2030-electro`/`jp-2030-melodic`/`jp-2030-anime`/`kids-0to2`/`kids-2to4`/`kids-4to7`)는 골격 값(가장 가까운 기존 프로파일에서 차용한 잠정 수치)만 채웠습니다 — 실제 값은 B1/C1/D1/E1/F1의 몫입니다.

아크 모델은 `ArcModelId = 'five-phase' | 'repetition-cycle'` 타입만 신설했습니다. `core/arcPlan.ts`는 여전히 `five-phase`만 실제로 구현합니다 — `repetition-cycle`은 타입과 프로파일 필드 값(kids 계열 프로파일에 지정)만 존재하고, 실제로 세트 5구간 곡선을 건너뛰는 로직은 없습니다. **미구현**으로 표시합니다(동요 워크스페이스를 실제로 만드는 D1/E1의 몫).

### 1-6. 브릿지 지시문 (TASK F)

`bridgeInstruction.ts`에 `buildResolvedConstraintsSection(constraints)`을 추가하고 `ClaudeCodeInstructionOptions.resolvedConstraints`로 노출했습니다. `buildClaudeCodeInstruction`이 이 옵션이 있으면 `[이 세트의 컨셉 제약]` 섹션을 넣습니다. 실전 출력은 §9-6에 있습니다.

**미구현(명시)**: 이 옵션을 실제로 채워 넘기는 UI 호출부가 없습니다. 조사 결과 기존 `setDirectorInterpretation` 옵션(v3.63부터 존재)도 마찬가지로 어떤 컴포넌트에서도 채워지지 않고 있었습니다(`Step3Generate.tsx`의 `buildClaudeCodeInstruction` 호출은 7-arg 형태로, `instructionOptions`를 전혀 넘기지 않습니다) — 이번 문서가 새로 만든 gap이 아니라 A3 이전부터 있던 gap과 같은 상태입니다. 함수 자체는 단위 테스트(§9-6)로 동작이 실측되어 있습니다.

## 2. 실제 버그 발견·수정 — `applyEraQuota`의 이중 차감

구현 중 실제 버그를 발견했습니다: 첫 버전은 `freed`(재배분 가능 곡 수)를 primary 버킷에 채운 뒤 `freed -= (toAdd - remaining)`으로 갱신했는데, 이후 "남은 걸 더 채우기" 블록이 `freed > toAdd`를 다시 비교해 **이미 소비된 곡 수를 두 번 빼는** 결과가 됐습니다. 실측: 18곡 입력 → 16곡 출력(2곡 소실). `tests/v420ConceptConstraints.test.ts`의 `total`assertion이 이를 즉시 잡아냈습니다.

수정: `distributeIntoPrimary(amount)`라는 단일 헬퍼로 통합해 "얼마나 실제로 채워졌는지"를 그 함수의 반환값 하나로만 추적하도록 재작성했습니다(§`src/core/constraints.ts`의 "v4.2 bugfix" 주석 참고). 수정 후 18곡 입력 → 18곡 출력 확인.

## 4. §11 "이후 문서와의 관계" — 자체 판정

B1(한국 2030)이 이 프레임워크 위에서 "데이터만 추가"로 끝나려면:
- `titlePatterns.ts`에 `fitsWorkspaces: ['kr-2030']` 패턴 추가 — **가능, 코드 수정 불필요** (인터페이스가 이미 이 필드를 갖고 있음).
- `vocabularyBanks.ts`에 `kr-2030` 뱅크 추가 — **가능, 코드 수정 불필요**.
- `AudienceProfile`의 `kr-2030-emotional`/`kr-2030-electro` 골격에 실제 값 채우기 — **가능, 코드 수정 불필요** (이미 골격이 존재).
- `WorkspaceDefinition.defaultAudienceProfileId`를 `'general'`에서 `'kr-2030-emotional'` 등으로 바꾸기 — **1줄 데이터 수정**.
- era 감지: `extractEraConstraint`의 정규식이 현재 서양 올드팝 시대 어휘(60/70/80년대)에 한정되어 있어, 2030 워크스페이스가 시대 개념 없이 순수 무드/장르 기반이라면 이 부분은 **자연히 `unspecified:true`로 통과**하므로 문제없습니다.

D1(동요 안전 정책)이 "데이터 추가"로 끝나려면:
- `safetyPolicyId`가 이미 `AudienceProfile`에 있어 D1이 값을 채우고 실제 정책 조회 로직만 새로 만들면 됩니다 — **코드는 소량 신규(정책 조회부), 기존 구조 변경 없음**.
- `arcModelId: 'repetition-cycle'`은 타입만 있고 `arcPlan.ts`가 이를 소비하지 않습니다 — **D1/E1이 실제 `repetition-cycle` 빌더를 새로 작성해야 합니다** (완전한 "데이터만"은 아님, 이 부분은 코드 작업이 남아있음을 명시합니다).

결론: 제목/어휘/오디언스-필드 세 축은 데이터만 추가하면 되는 구조가 됐습니다. 시대 축은 이번에 다룬 서양 올드팝 시대 어휘를 넘어서는 새 시대 개념(예: "쇼와"/"헤이세이")이 필요해지면 `extractEraConstraint`의 정규식 확장이 필요합니다 — 이 역시 코드 몇 줄이지 새 아키텍처는 아닙니다. 아크 모델만 실질적인 코드 작업(빌더 구현)이 남아 있습니다.

## 5. 하지 말 것 — 준수 확인

- 시대 필터만 조이고 끝내지 않음 — 제목(TASK C)·어휘 검사(TASK D)도 같은 constraints 구조로 처리.
- 시대 미지정 컨셉을 억지로 정하지 않음 — §9-2 세 번째 컨셉으로 실측 확인.
- 오디언스 안전 제약(`hardExclusions`)을 컨셉이 덮지 않음 — `resolveConstraints`가 `audience.hardExclusions`를 그대로 복사해 컨셉 텍스트와 무관하게 항상 포함.
- 제목 패턴은 `data/titlePatterns.ts`에 데이터로 존재, 코드(`lyricEngine.ts`)에 하드코딩하지 않음.
- 어휘 반복 검사는 advisory — `compositionScorer.ts`에서 `blocking`이 아닌 `advisory` 배열에 push.
- 동요에 5구간 아크를 강제하지 않음 — `repetition-cycle` 타입만 존재, five-phase 로직을 동요 프로파일에 적용하지 않음(다만 실제 대체 로직도 아직 없음 — §1-5/§4).
- `senior` 외 프로파일 실제 값 채우지 않음 — 7개 전부 골격.
- 보컬 다양성(v3.72)/가사 장면(v3.64) 되돌리지 않음 — 전체 테스트 스위트 통과로 확인(§9-7).
- `lyricEngine.ts`의 문장 생성 로직(`composeVerse`/`composeChorus`/훅 워드뱅크) 미수정 — `git diff`로 확인 가능한 변경분은 `titleFromHook`/`createTitleGenerator`/그 주변 헬퍼(모두 제목 생성부)뿐입니다.
- v3.62 "작곡하라" 방식 유지 — 브릿지 섹션이 문구 강제가 아닌 수치/카테고리 제약으로 전달(§9-6).
